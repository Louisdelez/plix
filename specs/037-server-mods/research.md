# Research: Server Mods + Client Sync

**Feature**: 037-server-mods
**Date**: 2025-12-19
**Status**: Complete

## Research Questions

### RQ1: Chunked Transfer Protocol Design

**Question**: What is the optimal chunked transfer protocol for payload synchronization?

**Decision**: Use a simple request-response chunked protocol with acknowledgments.

**Rationale**:
- 256KB chunks balance between overhead and memory usage
- Maximum 8 in-flight chunks prevents memory exhaustion (~2MB buffer)
- SHA-256 verification on complete payload (not per-chunk) reduces overhead
- Simple resend request mechanism for lost chunks (MVP)

**Alternatives Considered**:
- Per-chunk SHA-256: Rejected - excessive overhead for small chunks
- Streaming without acks: Rejected - no flow control, memory exhaustion risk
- UDP-based: Rejected - reliability issues, complexity, existing TCP infrastructure

### RQ2: Client Payload Cache Strategy

**Question**: How should client payloads be cached and indexed?

**Decision**: SHA-256 content-addressed cache with file-based storage.

**Rationale**:
- SHA-256 provides collision-resistant content addressing
- File-based storage persists across sessions
- Cache path: `~/.local/share/plix/mods/payloads/{hash}.bin`
- Metadata stored alongside: `{hash}.meta` (mod_id, version, timestamp)

**Alternatives Considered**:
- SQLite database: Rejected - adds dependency, overkill for simple cache
- Memory-only cache: Rejected - loses cache on restart, defeats purpose
- Mod ID + version indexing: Rejected - same payload content may differ across versions

### RQ3: Join Policy Configuration

**Question**: What configuration format for join policies?

**Decision**: Extend existing `server_mods.toml` with `[join_policy]` and `[sync]` sections.

**Rationale**:
- Consistent with Feature 036 configuration
- TOML is already used for server configuration
- Sensible defaults work out-of-box

**Configuration Schema**:
```toml
[join_policy]
allow_server_only = true       # Default: allow server-only mods
allow_payload_sync = true      # Default: allow payload sync
require_payload_sync = false   # Default: don't require sync capability

[sync]
max_payload_mb = 25            # Maximum payload size
chunk_size_kb = 256            # Chunk size for transfer
max_inflight_chunks = 8        # Max concurrent in-flight chunks
transfer_timeout_secs = 300    # Overall transfer timeout
```

**Alternatives Considered**:
- Separate config file: Rejected - fragmentation of configuration
- Environment variables: Rejected - less discoverable, harder to version

### RQ4: ModSetDescriptor Source

**Question**: Where does ModSetDescriptor data come from?

**Decision**: Build from lockfile (`mods.lock`) generated by Feature 036.

**Rationale**:
- Lockfile contains exact versions and SHA-256 hashes
- Single source of truth for reproducibility
- Already computed at server startup

**Data Flow**:
1. Server loads `server_mods.toml` (Feature 036)
2. Resolver generates `mods.lock` with resolved versions
3. `ModSetBuilder` reads lockfile and mod manifests
4. `ModSetDescriptor` constructed with runtime modes and payload hashes
5. Sent to client during handshake

**Alternatives Considered**:
- Scan installed mods at runtime: Rejected - lockfile is already computed
- Separate modset config: Rejected - duplication, risk of drift

### RQ5: Mod Manifest Runtime Extension

**Question**: How to extend mod manifest for runtime classification?

**Decision**: Add `runtime` field with enum values: `"server"` (default), `"client"`, `"both"`.

**Manifest Schema Extension**:
```toml
[mod]
id = "my-mod"
version = "1.0.0"
runtime = "server"              # server | client | both (default: server)
client_payload = false          # Whether mod has client data to sync
client_payload_files = []       # Files to include in client payload
```

**Rationale**:
- Explicit declaration prevents ambiguity
- Default "server" enables existing mods without changes
- `client_payload_files` enables selective file inclusion

**Alternatives Considered**:
- Implicit detection: Rejected - unreliable, magic behavior
- Boolean `server_only`: Rejected - doesn't handle "both" case
- Separate client manifest: Rejected - complicates mod structure

### RQ6: Network Channel Allowlist

**Question**: How to implement mod network channel security?

**Decision**: Allowlist-based channel routing with pattern matching.

**Implementation**:
- Server-to-client: Allowed on `mod:{mod_id}:*` for any loaded mod
- Client-to-server: Only allowed if mod declares channel in manifest
- Rate limiting: Via existing Feature 034 token bucket (20 msg/s, 8KB max)

**Manifest Extension**:
```toml
[mod.network]
allowed_client_channels = ["input", "config"]  # Client can send to mod:my-mod:input, mod:my-mod:config
```

**Rationale**:
- Prevents spoofing: client can't send on `mod:other-mod:*`
- Explicit allowlist reduces attack surface
- Leverages existing rate limiting

**Alternatives Considered**:
- No restrictions: Rejected - security risk, spoofing possible
- Per-message signing: Rejected - excessive overhead, complexity
- Capability tokens: Rejected - adds state management complexity

### RQ7: Integrity Verification Flow

**Question**: When and how to verify payload integrity?

**Decision**: SHA-256 verification after complete payload reassembly.

**Flow**:
1. Client receives `S2C_PayloadBegin` with expected hash
2. Client receives chunks and buffers to disk (temp file)
3. Client receives `S2C_PayloadEnd`
4. Client computes SHA-256 of temp file
5. If match: rename to cache, send `C2S_PayloadAck`
6. If mismatch: delete temp, disconnect with integrity error

**Rationale**:
- Single verification point is simpler
- Disk buffering prevents memory exhaustion
- Failed verification clears partial state

**Alternatives Considered**:
- Per-chunk verification: Rejected - increased overhead, 256 hashes for 64MB
- Memory buffering: Rejected - 25MB limit, but 100 concurrent = 2.5GB

### RQ8: Error Handling & User Messages

**Question**: What error messages for join refusal?

**Decision**: Structured error codes with human-readable messages.

**Error Codes**:
| Code | Message Template |
|------|------------------|
| `MOD_MISMATCH` | "Server requires mod '{id}' version {ver}" |
| `PAYLOAD_MISSING` | "Missing client data for mod '{id}'" |
| `SYNC_UNSUPPORTED` | "Your client doesn't support mod sync. Update to join." |
| `SYNC_TIMEOUT` | "Mod data transfer timed out. Try reconnecting." |
| `INTEGRITY_FAILED` | "Mod data verification failed. Reconnecting..." |

**Rationale**:
- Clear, actionable messages (SC-004: 90%+ player understanding)
- Codes enable programmatic handling
- Templates support localization

## Best Practices Applied

### From Feature 036 (Mod Distribution)
- Use existing `DistributionConfig` and `Lockfile` types
- Follow same SHA-256 verification pattern
- Consistent error code naming (EMREG prefix)

### From Feature 034/035 (Mod API)
- Use existing network channel infrastructure
- Apply token bucket rate limiting
- Follow event-driven update pattern

### Protocol Design
- Version ModSetDescriptor for future evolution
- Use bincode for efficient serialization (existing)
- Include protocol version in handshake

### Security
- Never trust client-reported state
- Verify all hashes server-side before accepting ack
- Timeout all transfers (300s default)
